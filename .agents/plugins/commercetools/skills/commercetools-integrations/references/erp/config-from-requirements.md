# Requirements → ERP connector config

Turns the Step 1 requirements table ([overview.md](./overview.md)) into concrete `connect.yaml` values. Give each one a one-line **why** when you present it.

**Where the keys come from.** For a **public connector**, the authoritative key list is its repo's `connect.yaml` and README — read those and use their names; the keys below are illustrative and will not match. For a **build**, these are keys you define, so the names are yours; what the ERP or middleware *needs* configured (endpoint paths, tenant/company codes, auth style, batch conventions) comes from that system's own documentation.

## The requirement → config map

| Requirement (Step 1) | Config / decision | Why |
|---|---|---|
| Which domains are in scope | One `deployAs` entry per flow | Separate integrations per domain is the documented best practice; it also lets you deploy them independently |
| Counterparty (ERP / middleware / gateway) | `standardConfiguration`: base URL + per-flow paths | The endpoint changes per environment and per customer landscape; never a constant |
| ERP/middleware auth | `securedConfiguration`: client id + secret, API key, or certificate material | Secrets never in `standardConfiguration`, never in code |
| Company / tenant / sales org | `standardConfiguration` | Multi-company ERPs need it on every call, and it differs between test and production |
| Cadence per flow | `properties.schedule` on each `job` | Overridable per deployment, so ops can retune without a release |
| Volume per flow | `standardConfiguration`: page/batch size, concurrency, max runtime per run | The knobs you will actually turn when a nightly run starts missing its window |
| Write API per domain | `standardConfiguration`: e.g. `PRODUCT_WRITE_MODE: import \| httpApi` | Explicit, because it changes idempotency and error handling |
| Order export trigger | `standardConfiguration`: Message types / order-state gate; Subscription registered in `postDeploy` | Exporting on the wrong trigger creates ERP documents for unpaid orders |
| Stock semantics | `standardConfiguration`: location → Channel map, safety buffer, low-stock threshold | Business decisions with a revenue cost; must be changeable without a redeploy |
| Price semantics | `standardConfiguration`: `PRICE_MODE: standalone \| embedded`, currencies/countries in scope, publish-or-stage | Wrong price model means a rebuild, not a patch |
| Mapping tables | `standardConfiguration` for small ones; CustomObjects for large or business-maintained ones | Onboarding one new plant must not need a release ([data-mapping.md](./data-mapping.md)) |
| ERP-down behavior | `standardConfiguration`: retry limits, retry-store TTL | The failure contract has to be operable without a redeploy |
| Region + project | `standardConfiguration: CTP_REGION`; scopes via `inheritAs` | Hosts and client provisioning are region/project specific |
| ERP sandbox vs production | `standardConfiguration`: environment flag | ERP test clients hold different master data; a mis-set flag posts test orders into production |

## The connect.yaml envelope

`connect.yaml` has **no published JSON Schema** — its shape is defined only by the [docs](https://docs.commercetools.com/connect/development.md). Use only documented envelope keys (`deployAs` with `name` / `applicationType` / `endpoint` / `scripts` / `properties` / `configuration`, the latter splitting into `standardConfiguration` and `securedConfiguration`; plus root-level `inheritAs`) and put the file at the **repository root** — a nested `connect.yaml` silently fails to deploy.

### Scopes (least privilege)

Declare scopes and let Connect mint the API client rather than hand-supplying `CTP_CLIENT_ID`/`CTP_CLIENT_SECRET`. If you take that route, the autogenerated variables must **not** appear in `connect.yaml` at all — declaring `CTP_PROJECT_KEY`, `CTP_CLIENT_ID`, `CTP_CLIENT_SECRET`, or `CTP_SCOPE` yourself means no API Client is generated, and the deploying API Client needs `manage_api_clients` or the deployment fails with `403` ([Automatically generate API Client credentials](https://docs.commercetools.com/connect/modify-connector.md)). The generated client's scopes are **connector-wide**: the only documented place for them is root-level `inheritAs.apiClient.scopes`, so there is no per-application scope list. Every application therefore gets the union below — keep it as small as the connector as a whole needs, and if the inventory job genuinely must not be able to write Orders, that separation has to come from splitting the connector or from supplying pre-created per-application credentials via `securedConfiguration`:

| Scope | Needed by | For |
|---|---|---|
| `manage_subscriptions` | order-export `postDeploy`/`preUndeploy` | register/remove the Order Subscription |
| `manage_orders` | order-export (read) and document write-back (write) | re-fetch the Order; `updateSyncInfo` and invoice Custom Fields |
| `manage_products` | product inbound **and inventory inbound** | Products and Variants — and `InventoryEntry` writes, which have **no scope of their own**, so an inventory-only application unavoidably gets product write too; say so rather than hiding it |
| `manage_product_types` | product inbound (only if it provisions Product Types) | classification mapping; drop it if types are managed by hand |
| `manage_channels` | `postDeploy` | create the supply/distribution Channels for ERP locations and the `SyncInfo` channel — prefer this over relying on `manage_products`' legacy coverage of Channels |
| `manage_standalone_prices` (`PRICE_MODE: standalone`) | price inbound | Standalone Prices are their own resource: `manage_products` does **not** cover them, and grants import requests for *Embedded* Prices only. With `PRICE_MODE: embedded`, `manage_products` is the one you need |
| `manage_customers` + `manage_business_units` | customer/B2B flows | Customers and Business Units are **separate scopes**; Associates are managed through the Business Unit |
| `manage_types` | `postDeploy` | Custom Types for ERP ids, invoice fields, sync markers |
| `manage_key_value_documents` | jobs and mapping lookups | checkpoints/cursors, retry store, mapping tables in CustomObjects |
| `manage_import_containers` | any Import API flow | Containers are their own scope; each **ImportRequest** additionally needs the scope for the container's `resourceType` (`manage_products` to import products, `manage_standalone_prices` for Standalone Prices, and the matching `view_*` scope to read its operations) — [Import API authorization](https://docs.commercetools.com/api/import-export/hosts-and-authorization.md) |
| `view_project_settings` | most flows (optional) | resolve configured currencies, countries, and languages instead of hardcoding them |

Confirm every scope name against the current [API scopes](https://docs.commercetools.com/api/scopes.md) reference — plus [Import API authorization](https://docs.commercetools.com/api/import-export/hosts-and-authorization.md), where the container scopes live — before shipping — an invalid scope fails client creation at deploy time, and `view_*` variants are not always separate scopes.

### Worked example — order export + master-data inbound + inventory

```yaml
deployAs:
  - name: order-export
    applicationType: event
    endpoint: /orderExport
    scripts:
      postDeploy: npm ci --omit=dev && npm run connector:post-deploy   # registers the Order Subscription + Custom Types
      preUndeploy: npm ci --omit=dev && npm run connector:pre-undeploy
    configuration:
      standardConfiguration:
        - key: ORDER_EXPORT_TRIGGER_STATE
          description: Order state that gates export, for example Confirmed; empty means export on OrderCreated
        - key: ERP_SALES_ORDER_PATH
          description: Path on the ERP or middleware base URL that accepts a sales order
          required: true
        - key: ERP_SYNC_CHANNEL_KEY
          description: Channel key used in SyncInfo to record that the Order reached the ERP
          default: erp

  - name: masterdata-import
    applicationType: job
    endpoint: /masterdataImport
    properties:
      schedule: '0 2 * * *'
    scripts:
      postDeploy: npm ci --omit=dev && npm run connector:post-deploy
      preUndeploy: npm ci --omit=dev && npm run connector:pre-undeploy
    configuration:
      standardConfiguration:
        - key: PRODUCT_WRITE_MODE
          description: "How product and price data is written: import (Import API) or httpApi"
          default: import
        - key: PRICE_MODE
          description: "standalone or embedded Prices"
          default: standalone
        - key: IMPORT_BATCH_SIZE
          description: Resources per Import API request (documented maximum is 20 — https://docs.commercetools.com/api/import-export/import-requests.md)
          default: '20'
        - key: PUBLISH_ON_IMPORT
          description: "'true' publishes imported products immediately; 'false' stages them"
          default: 'false'
        - key: MASTERDATA_CURSOR_CONTAINER
          description: CustomObject container holding the run cursor and last-success timestamp
          default: erp-sync-state

  - name: inventory-sync
    applicationType: job
    endpoint: /inventorySync
    properties:
      schedule: '*/15 * * * *'
    configuration:
      standardConfiguration:
        - key: LOCATION_CHANNEL_MAP
          description: "ERP location to supply Channel key map, for example PLANT01=warehouse-eu,PLANT02=warehouse-us"
          required: true
        - key: STOCK_SAFETY_BUFFER
          description: Units withheld from the published quantity per SKU
          default: '0'
        - key: LOW_STOCK_THRESHOLD
          description: Quantity below which a real-time ERP availability check is made
          default: '5'

inheritAs:
  apiClient:
    scopes:
      - manage_subscriptions
      - manage_orders
      - manage_products
      - manage_standalone_prices
      - manage_channels
      - manage_import_containers
      - manage_types
      - manage_key_value_documents
      - view_project_settings
  configuration:
    standardConfiguration:
      - key: CTP_REGION
        description: commercetools region, for example europe-west1.gcp
      - key: ERP_BASE_URL
        description: Base URL of the ERP API, middleware, or API gateway the connector calls
        required: true
      - key: ERP_COMPANY_CODE
        description: Company or tenant code sent with every ERP call
      - key: ERP_ENVIRONMENT
        description: "ERP environment: test or production"
        default: test
      - key: ERP_REQUEST_TIMEOUT_MS
        description: Outbound timeout per ERP call
        default: '10000'
    securedConfiguration:
      - key: ERP_CLIENT_ID
        description: Client id for the ERP or middleware endpoint
        required: true
      - key: ERP_CLIENT_SECRET
        description: Client secret for the ERP or middleware endpoint
        required: true
```

`inheritAs` carries what every application shares (region, ERP endpoint, credentials) so the same secret isn't declared four times, and the scope list is the connector-wide union described above — `manage_import_containers` is in it because `PRODUCT_WRITE_MODE` defaults to `import`. Mark every key the connector cannot start without `required: true`, so a missing value fails the deployment instead of the first run.

Every value above is a **decision you can defend**; if you can't say why a key exists, drop it. Envelope mechanics and the deploy flow: [deployment-installation.md](../../../commercetools-connect/references/deployment-installation.md).

## `postDeploy` has real work here

An ERP connector depends on commercetools resources existing before the first run. Make each step idempotent — get-then-create, never blind-create ([lifecycle-scripts.md](../../../commercetools-connect/references/lifecycle-scripts.md)):

- **Supply and distribution Channels** for every ERP location and sales organization in `LOCATION_CHANNEL_MAP`, plus the `ERP_SYNC_CHANNEL_KEY` used by `SyncInfo`.
- **Custom Types** for the ERP identifiers, invoice fields, and sync markers the flows write.
- **The Order Subscription** for the export flow, with the Message types the trigger implies; removed in `preUndeploy`.
- **The state container** for cursors, checkpoints, and the retry store.
- **Deploy-time credential and reachability validation** — one cheap authenticated ERP call, so a wrong endpoint, an expired secret, or an allowlist that doesn't include Connect fails the deployment instead of the first nightly run.

## Checklist
- [ ] Only documented `connect.yaml` envelope keys; file at the repository root
- [ ] One `deployAs` entry per in-scope flow; nothing declared that isn't in scope
- [ ] ERP endpoint, company/tenant code, and environment flag are config; credentials in `securedConfiguration`
- [ ] Schedules set per `job` and overridable per deployment; batch size and concurrency configurable
- [ ] Write API, price mode, publish-or-stage, buffer, and threshold all explicit config keys
- [ ] Mapping tables in config or CustomObjects; none in code
- [ ] Scopes are a **connector-wide union** kept as small as the connector needs (no per-application list exists); separation, if required, comes from splitting the connector or pre-created credentials; every name verified against the current scopes reference
- [ ] `postDeploy` provisions Channels, Types, Subscription, and state container idempotently; `preUndeploy` removes what it created
- [ ] `postDeploy` validates ERP credentials and reachability at deploy time
- [ ] ERP test-vs-production switchable by config, and defaulted to test
